01Executive summary

The three-project layout (Core / Cli / GUI) and the YAML-driven snippet catalog are the two strongest decisions in this codebase. They give a clean abstraction boundary and a way to evolve evasion content without recompiling.

The weak spots cluster in four risk areas:

Risk 1 Stringly-typed contract between UI and Core

UiData is three string→string dictionaries with heuristic key resolution. The pipeline assumes XAML control names will stay stable forever and assumes no benign control will accidentally match a heuristic.

Risk 2 God-class hotspots

CompilerService (3,083 LOC), MainFormCoordinator (1,707), PeBackdoorService (1,656), Cli/Program.cs (3,150). All mix orchestration, parsing, validation, rendering, repair, logging, and reporting.

Risk 3 Fragile post-hoc text-repair pipeline

Multiple regex patches (PatchBin2ShellPayloadLambda, RepairCStringLiteralQuotes, PatchCapturelessLambdas, WrapFetchWithHexDecode, SplitLargeCodeBlobText, InjectWebPayloadPreamble) all exist to fix the output of an external tool you also control (bin2shell). Each is a stand-in for a missing contract.

Risk 4 Supply chain is too trusting

RequirementProvisioner downloads bin2shell from GitHub main/master archive zips — no checksum, no signature, no version pinning. The whole offensive payload generator depends on whatever HEAD ships today.

Bottom line

The architecture is at the point where it works because the original author remembers all the implicit invariants. The next person — or the same person in three months — will start tripping on them. The plan below is sequenced to make those invariants explicit before adding more features.

The trust boundary issue: external tools (bin2shell, SGN, donut, MinGW, the C++ toolchain) are treated as in-process libraries even though they are out-of-process executables fetched from the public internet. There is no formal contract for what they emit. Every breakage manifests as a regex patch in C#.

03What's right (preserve these)

  • Core/Cli/GUI split. Real, enforced (Core has no WinUI). Keep this.
  • Interface-driven services (IAppPaths, ICompilerService, IBin2ShellRunner, ICompilerToolLocator, ICodeSnippetCatalogService, IRequirementProvisioner, IProgressReporter). Constructor injection is consistent and defensive.
  • YAML catalog as the unit of evolution. Decoupling techniques from the build is genuinely good.
  • Session directories (logging/session_<ts>_<slug>/{input,source,build} + report.txt/session.log) — excellent forensic posture for a security tool.
  • The requires: dependency contract between snippets (e.g. requires: [uac_bypass]) plus ValidateSnippetRequires — this is the right shape. It just needs more entries in RequiresTokenToSectionTemplate.
  • CppCompilationPlan as an explicit IR between input resolution and rendering.

04Critique — how things can break

4.1 The UiData contract is implicit, fuzzy, and lossy

UiData.TextBoxes/ComboBoxes/ListBoxes are Dictionary<string, string>. Keys come from XAML x:Name (GUI) or argv (CLI). Several services then do heuristic lookup:

  • CompilerService.TryGetEncoderIndex iterates all combo entries and matches any key containing "bin2" + ("enc" or "codec").
  • EncoderKeys / EnvelopeKeys / AntiEmulationSelectionKeys / ShikataMaxBytesKeys etc. are arrays of 4–11 alias strings each (CompilerService.cs:366-436).
  • YamlCodeSnippetCatalogService.MatchScore does prefix and keyword-overlap matching to find a section by template key.
How it breaks

Adding a benign XAML control whose name happens to contain bin2…enc… quietly hijacks encoder selection. Renaming a control silently zeros out encoder selection — the build still succeeds but produces a misconfigured loader. A typo in a YAML template: field is "rescued" by MatchScore and lands on whatever sorts first.

4.2 CompilerService is doing nine jobs

CompilerService.cs mixes:

  1. Validation of environment.
  2. Compiler discovery (delegated, but error-handled here).
  3. Snippet/template selection from the catalog (with fuzzy resolve).
  4. Shellcode source resolution (file/raw/url/web/generic).
  5. SGN orchestration (ApplyShikataGaNaiAsync, RunSgnProcessAsync).
  6. Bin2Shell orchestration + post-hoc repair of its output (5+ regex passes).
  7. Token substitution ({{TOKEN}}, $param$).
  8. Template rendering, including a regex-based InjectWebPayloadPreamble that finds main( to splice in #includes.
  9. Session log/report generation.

Plus 130+ lines of C++ runtime code embedded as a C# string literal (SharedPreamble, ProcessLookupHelper) that defines wash_track, wash_demand_elevation_or_shutdown, _wash_veh, etc. That C++ is loader behavior — it has nothing to do with the C# build orchestrator and shouldn't live in it.

4.3 The bin2shell-output repair pipeline is load-bearing wallpaper

These exist purely because bin2shell's emitted C++ doesn't compile cleanly:

  • PatchBin2ShellPayloadLambda — fixes capture-default lambdas at file scope.
  • PatchCapturelessLambdas — the inverse repair when the snippet lands in a function body.
  • RepairCStringLiteralQuotes — fixes base91 quotes on multi-line string literals.
  • RepairStringLine — per-line continuation of the above.
  • SplitLargeCodeBlobText — splits oversize literals.
  • WrapFetchWithHexDecode — wraps the fetch call.
  • InjectWebPayloadPreamble — locates main( via regex and splices includes.
  • Bin2ShellWebOutputParser.RepairCppEscapeSequences — repairs \r \n \0 mis-escaped through Python.
How it breaks

Every one of these is a silent fixup that depends on the exact shape of bin2shell's stdout. The day bin2shell changes its emitter (it's your own repo at 0xhmza/bin2shell, fetched from main HEAD), one or more of these pattern-matches stops firing and the C++ either fails to compile or, worse, compiles into a subtly broken loader.

4.4 Silent error swallowing

Multiple sites swallow exceptions with catch { }:

  • AppPaths.ActivePlaybookFullPath — falls back to default on any read error.
  • RequirementProvisioner.CleanupStaleDirectories, ClearDirectoryContents, TryDelete*, DeleteDirectoryWithRetry — every cleanup is best-effort and silent.
  • CppFileConverter.SourceContainsDllMain and DetectRequiredLibraries — read errors ignored. A missing winhttp link will only surface as a linker error.
  • CompilerToolLocator and CompilerService.TryDiscoverCompilerAsync — discovery exceptions become a soft null and a warn note.
  • YamlCodeSnippetCatalogService.TryParseYaml/Json — swallow YamlException/JsonException and try the other format. A genuine YAML syntax error produces "Snippet catalog is empty or invalid" with no line number.

These aren't all wrong individually — but as a pattern they make root-cause debugging painful, because the user reaches the failure several layers downstream from the cause.

4.5 Provisioner can leave a half-installed tool on disk

RequirementProvisioner.MoveDirectoryRobust has three strategies. Strategy 3 (ClearDirectoryContents then CopyDirectoryContents) wipes the target first and then copies. If CopyDirectoryContents throws midway, the target is left empty/partial. There's no rollback when only a subset of files copied. A failed install reports success on _logger.Ok(...) based only on the last operation completing without throwing.

4.6 Supply chain assumptions

RequirementProvisioner.GetMissingRequirements:

  • Bin2Shell: github.com/0xhmza/bin2shell/archive/refs/heads/main.zip — moving HEAD, no checksum.
  • SGN: pinned to v2.0.1 — fine.
  • Donut: pinned to v1.1 — fine.
The largest single foot-gun

A malicious PR/force-push to 0xhmza/bin2shell ships into every user's machine on next provision. For a tool whose entire purpose is generating offensive payloads, this is the wrong default. There's also no SHA-256 verification, no Authenticode check on the binaries, and no version pinning for one of the three downloads.

4.7 Cancellation isn't fully honored

  • RunSgnProcessAsync (CompilerService:803) — await process.WaitForExitAsync(cancellationToken). If the token fires, the wait is cancelled; the SGN process keeps running. Same pattern in Bin2ShellRunner.RunAsync.
  • CppFileConverter.ConvertAsync actually calls TryKill(proc) on OperationCanceledException. The good pattern is implemented in one of three places.

4.8 Two parallel placeholder systems with thin documentation

  • Template-level: {{TOKEN}} resolved by ApplyTemplateContent.
  • Snippet-level: $param$ resolved by SubstituteAndCollect.
  • Plus ad-hoc tokens: $guardrail_param$, __GUARDRAIL_PARAM__, $psname$ substituted manually in their respective Apply*Selection methods.

Three different placeholder dialects. None are formally documented in a schema file.

4.9 No DI container, no schema validation, almost no unit tests

  • DI: services are wired up by hand in TestHarness, in Cli/Program.cs, and in App.xaml.cs. Adding a service means three call sites change.
  • Schema: default.yaml is 2,895 lines with no JSON Schema, no $schema reference, no validator step in CI, no contract test that every section's requires: token resolves.
  • Tests: TestHarness is end-to-end smoke (compile + run the EXE). There are no unit tests on BuildPlaceholderValues, SubstituteTokens, ValidateNoUnresolvedTokens, Bin2ShellWebOutputParser, the regex repair passes, or CompilerToolLocator.

4.10 Process orchestration is duplicated four times

CppFileConverter.ConvertAsync, Bin2ShellRunner.RunAsync, CompilerService.RunSgnProcessAsync, DonutService.ConvertAsync, and MingwDownloader each implement their own ProcessStartInfo + redirect stdout/stderr + WaitForExitAsync + cancellation handling — with different behaviors on cancellation, output buffering, and exit-code interpretation. A common ExternalProcessRunner would unify them and let cancellation, timeout, and stderr-on-failure be solved once.

05Refactoring plan

Each step is independently shippable and unblocks the next. Branch each item; PR each individually.

Progress (live)

  • P0-3 (extract C++ runtime): ✓ done. SharedPreamble and ProcessLookupHelper moved to Assets/runtime/wash_runtime.h + wash_proc_lookup.h; CompilerService.cs shrank from 3,083 → 2,796 lines (–287). Loaded lazily via IAppPaths.
  • P0-4 (YAML schema + exact-match resolver): ✓ done. Published Assets/playbook.schema.json, swapped TryParseYaml/Json swallowing for line/column-aware error reporting, added ValidateCatalogShape with section/item context, deleted MatchScore/SharesKeyword fuzzy resolution, moved requires: token map to KnownRequiresTokens and validate at load.
  • P0-1 (typed UiData contract): ▶ in progress.

P0 — Foundations (do first; everything depends on these)

P0-1 · Lock down the UiData contract

P0 Effort: 2–3 days · Risk: medium (touches GUI, CLI, Core)
  • Replace UiData (three loose dictionaries) with a typed input record: CompilationRequest with explicit fields for shellcode source, encoding, SGN, template id, and a IReadOnlyDictionary<string, string> SnippetParams keyed by scoped key ({sectionTemplate}_{itemId}_{inputId}).
  • Move all heuristic key resolution (EncoderKeys[], TryGetEncoderIndex, GetAntiEmulationSelection, etc.) into a single UiDataAdapter in the GUI layer that converts visual tree → typed request. The adapter is the only place control naming knowledge lives.
  • The CLI builds CompilationRequest from argv directly without going through dictionaries.
  • Acceptance: removing every bin2…enc… substring scan and the *Keys arrays from CompilerService.cs.

P0-2 · Carve CompilerService into composable stages

P0 Effort: 4–5 days · Risk: medium · Strict refactor — no behavior change

Split into:

  • ICompilationPipeline (façade) — orchestrates stages.
  • IShellcodeSourceResolver — file/raw/url/web/generic.
  • IShellcodeEncodingPipeline — SGN, then Bin2Shell, then post-process. Returns a typed EncodedShellcode (bytes/text + metadata), not a fragment of C++.
  • ICppCodeGenerator — owns CppCompilationPlan building, snippet substitution, template rendering. Pure, testable.
  • ISessionRecorder — owns the entire logging/session_*/ tree. Subscribes to pipeline events.
  • ICppBuilder — wraps CppFileConverter.
  • CompilerService becomes a 100-line orchestrator that wires these together.

P0-3 · Move the embedded C++ runtime out of C#

P0 Effort: 1 day · Risk: low
  • Extract SharedPreamble and ProcessLookupHelper from CompilerService.cs (lines 26-330) into Assets/runtime/wash_runtime.h.
  • Ship as a real .h next to default.yaml. Reference from templates as #include "wash_runtime.h" and resolve at render time via IAppPaths.
  • Benefit: syntax highlighting, clang-tidy, separate diff history, can be unit-tested with a real C++ compile.

P0-4 · Define a YAML schema and validate at load

P0 Effort: 2 days · Risk: low
  • Publish Assets/playbook.schema.json (JSON Schema for the YAML structure: sections/items/inputs/templates/placeholders/requires).
  • YamlCodeSnippetCatalogService validates against it on load. Failures must include line/column, not just "empty or invalid".
  • Add a contract test: every requires: token in the shipped catalog must resolve via RequiresTokenToSectionTemplate. Today only uac_bypass is wired — the others are silent no-ops.
  • Replace MatchScore/SharesKeyword fuzzy resolution with exact template/header lookup. If the catalog uses inconsistent names, fix the catalog.

P1 — De-risk the integrations

P1-1 · Single ExternalProcessRunner abstraction

P1 Effort: 2 days · Risk: low
  • Build IProcessRunner.RunAsync(spec, ct) → ProcessOutcome { ExitCode, Stdout, Stderr, Duration }.
  • Spec encodes timeout, env, stdin, working dir, expected exit codes, and cancellation behavior (kill-tree on cancel — currently only CppFileConverter does this).
  • Migrate Bin2ShellRunner, CompilerService.RunSgnProcessAsync, DonutService, CppFileConverter to it.
  • One bug fix lands four times for free.

P1-2 · Replace bin2shell stdout repair with a stable wire format

P1 Effort: 3–4 days, including a coordinated change in 0xhmza/bin2shell · Risk: medium

The repair regex pile is paying interest on a missing contract. Fix the contract:

  • Define a JSON or YAML output schema in bin2shell — already partly done (cpp_includes, cpp_declarations, etc.).
  • Have bin2shell emit raw payload bytes (base64) + structured C++ fragments already free of escape damage and lambda-capture errors. The Python escape repair (RepairCppEscapeSequences) is a sign that bin2shell is using a non-raw Python string for what should be a raw block.
  • Once the upstream emits clean output: delete PatchBin2ShellPayloadLambda, RepairCStringLiteralQuotes, RepairStringLine, SplitLargeCodeBlobText, PatchCapturelessLambdas, WrapFetchWithHexDecode. Keep one parser; assert on shape; no fixups.
  • If you can't change bin2shell, at minimum: pin its version (replace main.zip with a tagged release zip) and add a contract test that runs bin2shell with a fixed input and asserts on the parser output.

P1-3 · Pin and verify external downloads

P1 Effort: 1 day · Risk: low

In RequirementProvisioner:

  • Replace bin2shell/main.zip with a tagged release URL.
  • Add Sha256 to RequirementData. Verify after download, fail loudly if it doesn't match.
  • Verify Authenticode signature on sgn.exe and donut.exe where signed; for unsigned binaries, hash-pin.
  • Replace strategy-3 of MoveDirectoryRobust (in-place clear-then-copy) with: copy to a sibling target.new, then atomic rename target → target.old, target.new → target, then delete target.old. No window where the install is half-wiped.

P1-4 · Honor cancellation in all process runners

P1 Effort: 0.5 day · Risk: low

Falls out of P1-1 — all spawners use IProcessRunner and all kill on cancel.

P2 — Quality of life and longevity

P2-1 · Introduce a DI container

P2 Effort: 1 day · Risk: low

Use Microsoft.Extensions.DependencyInjection. One composition root in Cli/Program.cs, one in App.xaml.cs, one in TestHarness. Adding a service stops touching three files.

P2-2 · Real unit-test surface

P2 Effort: 4 days · Risk: low

Washmachine.Core.Tests (xUnit). First-cut targets:

  • CppCodeGenerator token substitution (table-driven).
  • Bin2ShellWebOutputParser against captured fixtures from a pinned bin2shell version.
  • CompilerToolLocator discovery on a faked filesystem.
  • RequirementProvisioner.MoveDirectoryRobust — strategies 1 and 2 happy/locked paths.
  • ValidateSnippetRequires — every shipped snippet's requirements resolve.
  • ResolveShikataGaNaiOptions, ResolveTemplate — input parsing edge cases.

Keep TestHarness as an integration suite, separate from unit.

P2-3 · Structured errors over string notes

P2 Effort: 2 days · Risk: low

CompilerResult carries Notes : List<string> — fine for humans, useless for callers. Add IReadOnlyList<CompilationDiagnostic> with { Severity, Code, Message, Source, Line? }. CLI/GUI render diagnostics; humans still see the same text; programmatic callers can react.

P2-4 · Slim MainFormCoordinator

P2 Effort: 3 days · Risk: medium

Once UiDataAdapter (P0-1) exists and CompilationPipeline (P0-2) is in place, MainFormCoordinator shrinks dramatically. Split remaining responsibilities by page (MainPageController, WebPayloadController, BackdoorPageController, SettingsController). Aim for each to be <300 LOC.

P2-5 · Schema-validate the CLI argument surface

P2 Effort: 1 day · Risk: low

The CLI's allowed-options dictionary (CommandOptionCompletions) is the only place the arg shape is described. Use System.CommandLine or a similar parser so each RunEncodeAsync etc. has a typed parsed-args object instead of string scans.

P3 — Optional / nice-to-have

P3-1 · C++ source linting in CI

P3

Render every template × default snippets combination and run clang-format / clang-tidy on the output. Catches malformed snippet text in the catalog before it ships to a user.

P3-2 · Catalog editor mode

P3

A washmachine-cli playbook validate and playbook lint (already partially echoed by scan) — make it a first-class command.

P3-3 · Telemetry-by-session.json

P3

Emit a structured session.json (alongside report.txt) so red-team workflows can grep across past runs.

P3-4 · Sandboxed test harness

P3

Phase 3 today executes the produced EXE on the dev machine. Move that under a Windows Sandbox / WDAGUtilityAccount profile so smoke tests can't accidentally fire a real loader against the developer.

07The two things to change tomorrow

If only two items get done:

1 · P0-3 — extract the embedded C++ runtime

Get the embedded C++ runtime out of CompilerService.cs into a real .h. It's a one-day fix that immediately makes the loader auditable.

2 · P1-3 — pin and verify downloads

Pin bin2shell to a tag and add SHA-256 verification on every download. One day, removes the largest single "could ship a malicious payload" foot-gun.

Everything else builds on those.
